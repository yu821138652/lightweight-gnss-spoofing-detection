先给结论：最新模型是一个很合适的轻量基线，但不是当前问题的最终模型。现在卡住的主要原因不是 `TCN16` 太小，而是任务标签、输入信息、设备域偏移和独立 Session 太少。继续扩大模型或普通扫参，预期仍只是零点零几；真正可能带来明显提升的方向，是重新组织输入信息和任务层级。

## 1. 最新结果用了什么模型

最新的“欺骗区间内全部信号为正类”实验，仍然使用：

```
compact11 + TCN16 + stats MLP
```

具体结构是：

```
每个 signal_id 的 W5 原始序列
5 个历元 × 5 个特征
    ↓
两层因果 TCN，hidden=16
    ↓
16 维时序表示
                         ┐
11 维窗口统计 → MLP → 16 维 ├→ 拼接 → MLP → 0/1
                         ┘
```

原始分支的 5 个特征：

- `Cn0DbHz`
- `AgcDb`
- `ReceivedSvTimeUncertaintyNanos`
- `PseudorangeRateUncertaintyMetersPerSecond`
- `FreqBand`

统计分支的 11 个特征：

- C/N0：Last、Mean、Std、Slope
- AGC：Last、Mean、Std、Slope
- 接收机时间不确定度 Std
- `SignalHistoryRatioW5`
- `AgcObservedRatioW5`

`TCN16` 中的 16 是隐藏通道数，不是 16 层或 16 秒窗口。整个模型只有 1,880 个参数。模型实现见 [gnss_signal_baselines.py (line 313)](E:/GNSS/paper2/lightweight-gnss-spoofing-detection/models/gnss_signal_baselines.py:313)。

训练使用：

- AdamW，`lr=1e-3`
- weight decay `1e-3`
- dropout `0.1`
- class-balanced CrossEntropy
- batch 256
- 最多 30 epochs，patience 6
- train-only、按设备标准化
- validation Macro-F1 选择 checkpoint
- test 固定使用 0.5/argmax，不在 test 调阈值

最新四折的结果是：

| 指标                    | 结果   |
| ----------------------- | ------ |
| Overall pooled Macro-F1 | 0.8668 |
| Overall Session 等权    | 0.7524 |
| Static pooled           | 0.8851 |
| Dynamic pooled          | 0.7351 |
| Dynamic Recall          | 43.23% |
| Dynamic Session 等权    | 0.7033 |
| `dy_L5` Macro-F1        | 0.6394 |
| `dy_L5` Recall          | 22.31% |

注意：`dy_L5` 的 F1 比旧标签高，不表示检出能力明显提高。它的 Recall 只是从 21.20% 变成 22.31%；主要变化是原来算作 L1 假正的预测，在新语义下被重新算成了真阳性。完整对照见 [static_dynamic_signal_cv4_20260727.md (line 102)](E:/GNSS/paper2/lightweight-gnss-spoofing-detection/docs/static_dynamic_signal_cv4_20260727.md:102)。

而且这次属于标签语义敏感性实验，尚未替代正式的 target-band-only 基线。

## 2. 这个模型合适吗

要分任务看。

如果目标是“判断当前这颗卫星、这个频段是否被直接欺骗”，它是一个相当合理的轻量基线：

- 严格因果；
- 时序与统计特征兼顾；
- 参数少、训练快；
- 输出粒度就是 `signal_id`；
- 很适合做后续实验的固定对照。

但如果采用最新的“区间内所有信号都是正类”语义，它就存在结构性错配：

- 标签实际上是设备/历元级的；
- 同一时刻所有卫星共享相同标签；
- 模型却把 128 个信号槽展开后逐信号独立预测；
- 各卫星之间、L1/L5 之间完全没有信息交换。

也就是说，我们要求某颗几乎没有变化的非目标频段信号，仅凭自己的 W5 特征判断“设备此刻正处于攻击事件”。这件事本来就很困难。动态新增非目标频段 Recall 只有 16.77%，正好印证了这种错配。

所以我的评价是：

> 当前模型适合继续作为可审计的逐信号基线，但不适合作为“全区间事件标签”任务的最终模型。

## 3. 应该调参数，还是改模型

不建议继续把主要精力放在扩大模型或大范围扫参上。

已有诊断里：

- TCN16 扩到 TCN32，参数从 1,880 增至 6,296，难例反而退化；
- LSTM/GRU 主要是在 Recall 和 FAR 之间互换，没有同时改善；
- 普通窗口搜索和统计特征消融没有出现质变；
- state-stratified validation 从约 0.898 提升到 0.930，但完整未见 Session test 基本不变。

最后一点很关键：这更像模型学到了同一 Session、设备和环境中的捷径，而不是经典意义上的“大模型记住训练集”。因此，加 dropout、减参数或增加训练轮数都不会从根本上解决。

参数层面仍可以做少量低成本确认：

- `lr={3e-4, 1e-3}`
- dropout `{0.1, 0.3}`
- Session/场景均衡采样
- 2–3 个随机种子
- 只在 validation 上选择阈值，报告 Recall@固定 FAR

其中阈值校准可能改善工作点，但不能改善正负样本的分数排序。Mate40、K60 等设备的问题已经证明，很多时候不是阈值不合适，而是排序本身就不好。

CNN+LSTM、TimesNet或者多模型集成也不应优先。尤其在 W5 只有 5 个时间点时，更复杂的时序模型没有足够的时间信息可利用。

## 4. 真正值得改的模型结构

我更建议保留当前的小 TCN 作为“每颗信号的编码器”，然后增加跨卫星上下文：

```
每颗 signal 的 W5/W30 时序编码
              ↓
同一设备、同一历元的信号集合聚合
区分 L1/L5，计算跨卫星共模和频段联动
              ↓
       设备攻击事件头
              ↓
将事件上下文送回每颗 signal
              ↓
       逐 signal 欺骗头
```

实现上可以用 DeepSets、attention pooling 或稳健统计池化，不必上大型 Transformer，几万参数就足够。

最好采用双任务：

- 事件头：预测“设备当前是否处于 reviewed 欺骗区间”；
- 信号头：预测“当前信号是否被直接欺骗”。

对于单频攻击中的非目标频段，不必强行全部标成 0 或全部标成 1，可以标为：

```
attack-associated / uncertain
```

训练逐信号头时忽略这些不确定标签，事件头仍然使用区间标签。这样就不必在两种都不完全合理的硬标签之间二选一。

## 5. 输入数据最值得做什么

当前已经做了 train-only 的按设备标准化，因此仅仅再做一次普通 z-score 意义不大。更值得尝试的是：

1. 因果相对基线

用每个新 Session 开始阶段的清洁数据，为每个设备、signal 建立 C/N0 和 AGC 的 median/MAD 基线，输入：

```
当前值 - 初始清洁基线
当前值相对基线的 robust z-score
```

这比不同设备之间直接比较绝对 AGC 更合理。但需要处理“采集一开始就处于攻击”的情况。

1. 跨卫星、跨频段特征

例如同一设备、同一历元内：

- L1/L5 的 C/N0 中位数、分位数和离散程度；
- 同时上升/下降的卫星比例；
- L5−L1 差值；
- 多颗卫星变化方向的一致性；
- AGC 与全体 C/N0 的共同变化；
- 可见卫星数和信号丢失比例。

欺骗往往不是某一颗卫星的孤立现象，这些信息可能比继续增加单信号统计量更有效。

1. 多时间尺度

保留 W5 处理瞬时变化，同时增加 W30/W60 的低频趋势或因果摘要。动态攻击的变化比较缓慢，W5 内可能近似不变；增大 hidden 并不会让模型看到更长历史。

1. 重新利用原始日志字段

原始 Android 日志实际上还能解析：

- 实际伪距率；
- 计算伪距；
- ADR/载波相关字段；
- 时钟 Bias、Drift；
- MultipathIndicator；
- Baseband C/N0；
- tracking state 等。

当前 processed CSV 只保留了很小一部分，见 [04_build_labeled_processed_csv.py (line 101)](E:/GNSS/paper2/lightweight-gnss-spoofing-detection/pipeline_total/04_build_labeled_processed_csv.py:101)。这些字段应先做设备覆盖率和缺失率审计，再决定哪些能进入模型。

## 6. 数据增强可以怎么做

可以做，但必须保持 GNSS 时序和设备级物理一致性。

比较合理的增强：

- 对一个完整设备窗口统一施加小幅 C/N0/AGC offset 和 scale，模拟设备标定差异；
- 对同一历元随机丢弃少量卫星，模拟遮挡和信号短暂丢失；
- 在不跨标签边界的前提下做时间裁剪或小幅 endpoint 抖动；
- 添加平滑、时间相关的测量噪声；
- 随机屏蔽部分低可靠特征，减少模型过度依赖 AGC；
- 按 Session、设备、场景、频段做均衡采样。

不建议：

- SMOTE；
- 每个点独立添加大噪声；
- 随意 time warp；
- 将不同 Session 的信号直接 Mixup；
- 复制动态 L5 endpoint 当作“增加数据”。

这些方法会增加行数，却不会增加新的设备响应、日期、路线或攻击条件。

## 7. 这是不是现有数据集的上限

我的判断是：

- 对“W5 + compact11 + 独立逐 signal + 当前硬标签”这条具体路线，已经非常接近实践上限；
- 对现有原始日志包含的信息，还不能说到达理论上限；
- 对现有 24 个 Session 能支持的“可信泛化结论”，确实已经接近上限。

目前只有 24 个完整 Session，`dy_L5` 只有 4 个。近 300 万 endpoint 高度相关，不能等价为 300 万独立训练样本。

如果只继续调 hidden、dropout、学习率、窗口，合理预期大概是：

- Overall 提升 0.005–0.02；
- 动态或个别场景提升几个百分点；
- 很难把 `dy_L5` Recall 从约 22%直接提升到可用水平。

如果改成跨卫星上下文、多尺度、双任务并重新利用原始物理字段，局部提升 0.05–0.10 是有可能的，但目前不能保证它会跨新 Session 泛化。

真正最有价值的数据仍然是新的独立动态采集：

- 不同日期和路线；
- 不同攻击功率和启动方式；
- 更多动态 L5；
- 更多设备状态；
- 更可靠的时间区间和攻击配置记录。

## 8. 如果让我从头接手

我不会先选 CNN、LSTM 或 Transformer，而会按下面顺序来：

1. 明确三个概念：正常、直接欺骗、攻击相关但是否直接欺骗不确定。把事件标签和卫星标签分开。
2. 重新锁定评估：完整采集事件隔离；主指标改为 Dynamic Session 等权、`dy_L5` Recall@固定 FAR、最差设备表现，而不是 Overall pooled。
3. 做模型无关诊断：检查每种特征在不同设备/Session 下的可分性；训练一个只用设备、场景、频段元数据的诊断模型，测量数据捷径有多严重。
4. 审计原始日志字段，构建因果相对基线、跨卫星共模、L1/L5 联动和多尺度特征。
5. 建立三个强基线：逻辑回归/LightGBM、当前 TCN16、轻量分层双头模型。所有模型使用完全相同的 split。
6. 实验分两阶段：先在固定开发折筛查，只有 Dynamic Session F1 提高约 0.05，或者 `dy_L5` 在相同 FAR 下 Recall 提高至少 10 个百分点，才跑完整四折。
7. 最后使用新采集、从未看过的 Session 做一次真正盲测。现在这些 outer test 已经多次参与方向判断，严格来说已经逐渐变成开发集。

一句话概括：

> 我认为目前卡住的是“逐信号局部表示的上限”，不是 TCN16 的参数上限。下一步若仍继续普通调参，价值很低；若重新处理标签层级、跨卫星信息和原始物理特征，仍值得再做一轮有明确停止条件的探索。
